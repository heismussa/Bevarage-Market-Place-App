BeverageMart Frontend Task Breakdown

Three developers · Customer mobile app + Store owner dashboard · 5 weeks · Backend API v1

How to read this document. Every task is small (a quarter of a day to two days). Each has an ID (for example A-07), the work, how we know it is done, the size in days, and the tasks it waits for. Put each task on your board (Trello, GitHub Projects, Jira) as one card, and use the ID in the branch name and pull request title, for example feat/A-07-token-refresh. Read docs/FRONTEND_HANDOFF.md before starting; it has every endpoint, error code and sample response.

Demo script (what the finished product must do)

  1. Owner signs up on the dashboard, creates a store, uploads a logo, adds products.
  2. Customer signs up on the phone, allows location, sees the store on Home, opens it, adds two products, checks out with M-Pesa.
  3. Run simulate_mobile_money; the payment screen changes to "Paid".
  4. The owner's bell shows the new order; the pending count goes up.
  5. Owner accepts, prepares, marks ready and completes. The customer's tracking screen follows each step and the bell shows each update.
  6. Stock goes down; a low-stock alert appears when a product reaches its alert level.
  7. Dashboard and analytics show the sale.
  8. Customer uses "Forgot password"; the code is read from the backend log.

Team rules

  • Git: nobody pushes to main. One branch per task (feat/B-11-cart-screen), a small pull request, one review by a teammate, then merge.
  • Commits: short and clear, for example feat(customer): add cart screen.
  • Secrets: never commit .env, demo passwords, tokens or the payment secret. App env files hold only the API URL.
  • Shared code: only A changes packages/api and packages/ui-tokens; others ask A or open a small pull request.
  • Backend: nobody edits the backend. Send questions to the project lead with the request, the response and the error.code.
  • Every morning: pull main; if docs/openapi.yaml changed, run npm run gen:api.
  • Meetings: 15-minute check-in every day; demo on seeded data every Friday.

Definition of done (every task)

  • Uses the generated API types; no hand-written response types.
  • Has loading, empty, error and success states.
  • Handles the error codes the endpoint can return; field errors appear under the right input.
  • Never calculates prices, totals or statuses; shows the values the server sends.
  • Buttons that call the API are disabled while the request is running.
  • Checked against the mockup and the "must / must not" list in the handoff.
  • npm run lint and npm run typecheck pass; reviewed by a teammate.
